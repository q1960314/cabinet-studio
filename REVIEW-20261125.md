## What went right (mechanisms, not luck)

1. **Capability test before building.** The pizza example proved the full
   pattern (manifest + resolved network + runtime + boot + scripted-model
   run) before any Cabinet Studio code existed. Every later step reused
   that pattern instead of reinventing it.
2. **SPEC before code, numbers fixed.** The catalog (8 items, dimensions,
   finishes, extras, integer-cent prices), the network (1 front + 2
   specialists), the 4 actions and their refusal rules, and T1–T8 were
   written first. No placeholder survived into the build.
3. **Template test suite adapted, not skipped.** The skill's template
   suite (dialog words, refused calls, bundled forms, consent focus,
   CRUSE) was ported in full (22 tests) rather than replaced by a few
   happy-path checks. It caught a real product defect (focus move) and a
   real test defect (shadowing) that happy-path checks would have missed.
4. **Shared-state discipline in tests.** Tests share one page and run in
   order, so absolute assertions were replaced with state-relative ones
   (read `before`, compute expectations from it, `clearQuote` helper for
   deterministic setup). The two absolute assertions that slipped in were
   caught by reasoning before the run, not by a flaky failure.
5. **Verification through the booted engine, not a parallel harness.**
   The browser script drives scripted turns through
   `window.__cabinet.engine` (the runtime the page actually booted), so
   the dialog path exercised is the visitor's path, not a test-only path.
6. **Every failure produced a fix in a real file.** The focus defect was
   fixed in `script.js`; the CRUSE schema assumption was fixed in the
   test to assert what the runtime actually provides; the bridge probe
   was fixed in the verification script. Nothing was fixed by weakening
   an assertion.
7. **No keys, no logins, no publishing anywhere.** BYOK only; the visitor's
   own key, never hardcoded. The task's constraints held for the whole
   build.

## Failures, with root causes

1. **Test file left syntactically incomplete (part 1).** The adaptation
   was written in two parts and part 1 ended mid-class. Root cause: a
   long file written in one pass without a closing check. Patch: part 2
   appended the remaining methods and registrations; the suite now runs
   end to end. Lesson for next time: run the suite after part 1 to catch
   the incomplete state immediately, instead of assuming the append will
   close it.
2. **`issueQuote()` moved focus to the confirmation section.**
   Root cause: the page code focused `#confirmation` on issue, which is
   fine for a manual button click but wrong for an agent tool call — the
   chat owns focus. The template test caught it. Patch landed in
   `script.js` (focus call removed); the confirmation section is still
   unhidden and visible.
3. **CRUSE test asserted a tool-schema wire format this runtime does not
   have.** Root cause: the template was written against an older runtime
   where the `render_cruse` schema carried the component wire format;
   the skill runtime keeps that guidance in the system prompt instead
   (`agentPresentationContext` + the website-operations line). The test
   now asserts the strings the runtime actually sends. Patch landed in
   the test. Lesson: when a template assertion fails, check the runtime
   actually in use before assuming the product is wrong — but also check
   the product first (failure 2 was the product).
4. **Variable shadowing in the CRUSE widget test.** A local `presentation`
   holding the tool schema shadowed the outer `presentation` object, so
   the stub sent the JSON Schema to `render_cruse` instead of the form.
   Root cause: same name reused in a nested closure. The trace of the
   dispatched tool call exposed it (args were the schema, not the form).
   Patch landed: renamed to `presentationSchema`. Lesson: when a tool
   call fails with a validation error, read the dispatched args in the
   trace before theorizing about the runtime.
5. **Bridge probe checked the wrong file.** The first browser check
   looked for `query_catalog` in the generated bridge HTML shell, which
   names no action; the action is registered by `bridge-actions.js`.
   Root cause: assuming the generated file's contents. Patch landed in
   the verification script (fetches `bridge-actions.js`). The product
   was never at fault; the Node test had already proven the sharing.
